# 垃圾询盘过滤与历史复查

新提交的明确广告保存为 E，不发送邮件或飞书通知。正常或无法确认的询盘仍为 D；系统不自动分配 B。有效工作队列不包含 E，管理员可在 E 类中复核并恢复。

## 历史预览（不写数据库）

在 server 目录运行，必须明确指定现有数据库的绝对路径：

```sh
node review-inquiries.js /absolute/path/inquiries.db
```

输出 automatic（可自动转 E）与 manualReview（受保护、需要人工复核），包含记录 ID、原等级、目标等级、分类原因及保护原因，不打印原始联系方式或正文。A/C/E 不参与。没有命中规则的记录保持不变。

只有自动分类、状态为 new、无备注、跟进日期或处理时间的明确垃圾 B/D 可自动变更。人工评级、旧状态迁移等来源一律保护；旧 B 的来源不明确时，不推断它是垃圾。历史低信息模板需要复核，不自动批量降级。

## 经确认后执行

先检查预览清单，暂停询盘服务以避免在途通知和业务写入，再执行：

```sh
node review-inquiries.js /absolute/path/inquiries.db --apply
```

执行前会用 SQLite 备份 API 在数据库同目录的 backups/spam-review-随机目录/before.db 保存完整备份（含已提交 WAL 数据）。备份失败则不变更。变更与审计记录在同一事务完成；已发送或失败的通知状态保留，仅 pending 改为 skipped。运行后恢复服务。

审计表 inquiry_spam_review_audit 保存变更前完整记录、目标等级、判定原因、时间与备份路径。备份与审计含客户资料，应限制访问并按现有数据库备份策略保管。少量误判优先在后台恢复；整库恢复仅限停服且确认不会覆盖后续业务写入时使用备份，不要在线覆盖数据库。

重复执行不会再次改判 E；人工恢复的记录只进入复核清单，不会被反复自动降级。启动 API 不再执行历史垃圾批量改判。

## 上线检查

本地修改不会自动上线。部署前确认线上 API 部署对应提交，而非仅前端部署成功；现有部署流程独立发布 server 目录。核对运行服务器上的 inquiry-classifier.js、index.js 与本次发布版本一致，再用经授权的测试记录验证 E 入库、通知跳过、工作队列排除。未访问服务器时不能宣称已核实线上版本或已清理线上历史数据。
